✦ VibeKit Architecture

One engine, many thin doors. Every capability is a tool with one contract; every host is a disposable adapter; every kind of state has exactly one deliberate home — and none of them is a database. This is the shape that makes agent-driven Algorand development safe to automate.

1 tool contract
53 tools (fully granted)
4 doors
7 harnesses via init
11 packages
0 databases
~190 tests

System map

Agents enter through whichever door their harness supports; every door is a small adapter over the same core (resolveDeployment → executeToolCall). The dashed territory is Phase 7–8: a second repo that may consume only published packages — the boundary that keeps the framework honest.

Custody boundary

The §6 rule that makes agent autonomy safe: agents wield capabilities and see metadata; key material and credential plaintext live behind the daemon and never cross into a context window. Credentials enter through human channels only.

State ledger

The §10 invariant, itemized. Every category of state that came up across three weeks of field sessions, and its single home. "Current account" and "current network" appear nowhere below — by design.

Bootstrap path

What a new developer (or their agent) actually does. Three grants are human-by-necessity — custody, faucet identity, harness trust — and each happens once per machine. Everything after is a sentence to an agent.

1
vibekit new my-app
template + skills + AGENTS.md + MCP config, one command
2
vibekit localnet start
AlgoKit-free chain in Docker
3
vibekit keystore serve
grant custody — daemon auto-provisioned, pinned
4
vibekit dispenser login
optional: grant testnet funding, refresh-token backed
5
claude · pi · grok …
approve the MCP server, then just ask
